# CooCoo MVP 產品方向決策紀錄

- 日期：2026-08-25
- 文件狀態：產品方向已確認；版本整合策略待確認
- 比較基準：`main@a10c6b7`、`legacy-720-development@7862ce1`
- 文件目的：整理產品討論中已確認的決策、版本差異、範圍邊界與後續待辦

> 本文件是整理後的決策紀錄，不是逐字對話，也不包含工具操作過程。

## 1. 產品目標與使用者

CooCoo 的第一批核心使用者是小資族、租屋族與外食族。產品要陪伴他們逐步減少外食，在有限的預算、廚具、時間與居住空間內開始自煮，並看見省錢與健康行為的累積成果。

主要使用情境是使用者在手機上：

1. 決定今天或這週要吃什麼。
2. 在超市或市場取得食材與份量建議。
3. 回到自己的小廚房，跟著步驟完成料理。
4. 確認實際省下的金額，推進自煮與圓夢目標。

因此，MVP 應以手機優先、短步驟、低輸入負擔和可持續陪伴為設計原則。

## 2. 成功指標

### 主要指標

- 使用者相較於自己的基準，少吃幾餐外食。
- 使用者透過自煮實際省下多少錢。

### 健康行為指標

- 自煮次數。
- 一段期間內吃到的蔬菜種類。

健康成果先記錄可驗證的行為，不宣稱精確減少多少鈉、脂肪或疾病風險。若未來要提供營養或健康數字，必須另行定義資料來源、計算方式與風險揭露。

## 3. 核心產品循環

MVP 最需要完整打通的循環為：

1. **設定目標**：設定一週想減少的外食餐數，並建立省錢與自煮目標。
2. **決定餐點**：依現有食材、即期狀況、預算、廚具與飲食禁忌，協助選擇今天或本週餐點。
3. **產生採買建議**：列出還需要購買的食材與份量。
4. **陪伴採買**：使用者在超市或市場勾選、調整或補充購買內容。
5. **發票入庫**：掃描後產生結構化資料，由使用者確認修正，再加入庫存。
6. **陪伴料理**：提供可免手操作的逐步料理流程與計時。
7. **完成結算**：扣除實際使用的庫存，確認本餐自煮成本與省下金額。
8. **呈現進度**：更新少吃外食、自煮、健康行為與圓夢進度。

這個閉環是 CooCoo 與一般食譜網站最重要的差異，功能優先順序應以能否完成此循環判斷。

## 4. 已確認的功能決策

### 4.1 首次使用設定

第一次使用必須取得：

- 使用者擁有的廚具。
- 飲食禁忌。
- 現有食材。
- 每天可用於餐費的預算。

這些資料是餐點與採買建議的必要條件。登入、跨裝置同步與資料備份也屬於第一批真實使用者需要的能力；後續應將 Auth、使用者資料所有權、後端 repository 與前端狀態真正串接，而非只依賴單一瀏覽器。

### 4.2 採買建議

MVP 只需要告訴使用者：

- 該買哪些食材。
- 每項食材需要多少份量。

MVP 不提供全聯、家樂福或傳統市場的即時商品、價格、庫存與優惠推薦，也不自行下單。這可避免在沒有穩定商業資料來源時做出不可靠承諾。

### 4.3 發票掃描與入庫

發票掃描後至少要產生以下六項資料：

1. 品名。
2. 數量。
3. 實際價格。
4. 購買日期。
5. 保存位置。
6. 預估期限。

系統先產生草稿，使用者只需確認或修正；確認後直接形成庫存資料，不要求重新輸入。辨識信心不足或缺少必要欄位時，應明確標出待確認項目，不應靜默猜測。

### 4.4 料理語音與離線界線

站在廚房時，語音至少要支援：

- 下一步。
- 上一步。
- 重複。
- 開始計時。
- 還剩多久。
- 完成料理。

料理開始後，已載入的食譜、步驟、計時與完成紀錄等核心流程應可完全離線使用。AI 生成或重新推薦等功能可以需要網路；離線時必須清楚說明，不能讓已開始的料理流程中斷。

### 4.5 功能可見性

- 保留發票掃描。
- 保留語音輸入。
- 保留 AI 採買助手。
- 開發者選單不得出現在正式使用者介面；只能在明確的開發或測試環境啟用。

### 共同缺口

不論選擇哪一個版本作為後續基礎，都仍需要補齊：

- 符合本次決策的首次設定流程。
- 「今天／本週吃什麼」的完整決策體驗。
- 真實發票辨識與可修正的入庫流程。
- 真實料理語音控制。
- 料理開始後的完整離線保證與恢復同步。
- Supabase Auth、資料所有權、跨裝置同步與備份。
- 正式環境的開發者功能隔離。
- 從採買到料理、結算、目標進度的端到端驗證。

## 6. 版本整合策略（待確認）

目前建議是：**以 `main` 的技術骨架作為核心，選擇性移植 `legacy-720-development` 的品牌視覺、行銷內容、陪伴感與遊戲化呈現。**

理由如下：

- `main` 的共用契約、集中式業務規則、原子操作與統一驗證流程，比較適合繼續接真實 Auth、資料庫與離線同步。
- `main` 的手機底部導覽更貼近超市、傳統市場與廚房的主要使用情境。
- `legacy-720-development` 的品牌敘事、3D 圓夢回饋、任務與內容網站更能表現 CooCoo 的陪伴感與差異化。
- 直接以展示版持續疊加真實資料能力，會先需要處理分散狀態、前後端未完全串接與開發工具外露等問題。

這只是待確認建議，**尚未成為正式技術決策**。在使用者明確確認之前，不應據此大規模搬移或刪除任一版本。

## 7. 尚待確認事項

1. 是否正式採用「`main` 技術骨架 + `legacy-720-development` 精選視覺與內容」的整合策略。
2. 每週「少吃幾餐外食」的基準期、目標設定方式與實際省錢公式。
3. 登入方式及首次設定與登入的先後順序。
4. 發票 OCR 的供應方式、辨識信心門檻與無法辨識時的手動流程。
5. 離線料理需要預先快取哪些食譜、圖片、語音能力與計時狀態，以及恢復連線後的衝突處理。
6. 哪些遊戲化元素應進入 MVP，哪些只保留為後續增強。

## 8. 建議下一步

先確認版本整合策略，再以核心循環為邊界建立一份可驗收的 MVP 路線：依序完成登入與首次設定、今天／本週餐點決策、採買與發票入庫、離線料理、完成結算及進度回饋。每一階段都要使用真實使用者資料完成端到端驗證，避免只增加可見但未串接的入口。
