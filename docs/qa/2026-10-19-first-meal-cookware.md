# 第一餐流程：廚具設定與推薦診斷

## 問題與修正

- 正式站「我的 → 廚具設定」只讀取既有廚具，空清單時沒有新增入口；「完成設定」只關閉視窗。現改為可新增、直接編輯名稱／類型及容量、取消或明確儲存的表單。
- 儲存沿用受登入保護的 `PUT /api/v1/settings/cookware` 與既有 `replace_cookware` 交易，不新增 migration。保留原廚具的 limitations，寫入後重新讀取資料庫；不修改庫存。
- 空白名稱由契約拒絕；表單阻擋重複名稱，儲存失敗保留草稿以供重試。
- 本機預覽的廚具設定同步更新推薦使用的 onboarding profile，避免畫面與推薦讀取不同清單。
- 重新檢視主廚檔案時，以最新雲端 profile 初始化草稿，避免調整用餐人數時帶入舊廚具。
- 今日頁在庫存、廚具或主廚檔案更新後重抓推薦；空結果依實際篩選原因說明未登記廚具、缺料、數量／單位、已安排菜色或食譜庫缺口，並提供自由搭配入口。
- 「補買前確認」不再被 disabled 屬性阻擋；仍須走原有預覽與確認，不能直接料理缺料食譜。

## 正式資料唯讀診斷（2026-10-19）

- 回報帳號廚具清單為空，主廚檔案保存 1 人份；本次使用者要求 2 人份。
- 庫存已包含葉菜、水果及雞蛋；雞蛋以盒記錄，不能自行換算成顆，葉菜的包也不能自行換算成克。
- 已發布食譜 25 道，補買參考價 25 筆且均已超過有效期。不得修改參考價日期來假裝有效。
- 使用唯讀快照在本機以快煮鍋、電子壓力鍋及 2 人份重算，inventory_only 與 small_purchase 均為 0 道合格食譜：缺少現有食譜所需的主食、蛋白質或調味料，並存在單位待確認項目。補齊廚具不代表現有食材就能滿足食譜庫。
- 不改寫使用者庫存、不放寬過敏硬限制、不捏造料理完成或 AI 成功。第一餐須待使用者確認實際數量、可用調味料及選定料理後繼續。

## 驗證邊界

- 單元／API 測試 191 項通過；新增廚具瀏覽器回歸 3 項通過（空清單新增、編輯後重新整理、庫存不變、取消、重複名稱、失敗重試）。
- 完整 `bun run verify` 通過：191 項單元／API 測試、Web build、API typecheck、30 項瀏覽器測試。Lint 僅有既有 providers.tsx 的 Fast Refresh 警告；瀏覽器使用 MSW，未啟動本機 API，連線檢查曾出現 health proxy ECONNREFUSED，測試全部通過。
- 正式站發布與真實帳號寫入讀回：待驗證。
- iPhone Safari／Android Chrome 真機與實際第一餐料理、庫存扣除、餐份及 EXP：待驗證。

## 後續：自由搭配備援與第一餐阻斷

- 廚具修正版已合併發布（PR #32）；正式帳號已由表單保存兩項設備、重新整理讀回，並透過三步設定保存 2 人份，庫存與 EXP 保留。
- 使用者確認雞蛋 32 顆、小白菜 250 克及有鹽有油後，原批次已依確認更正，未重複新增；鹽油總庫存未知，不建立虛構數量。
- 正式自由搭配的 AI 請求失敗後，卻回傳需要白飯與瓦斯爐的蛋炒飯。根因包含備援未檢查實際庫存與份量，且電器被當成瓦斯爐的通用替代。上游 AI 失敗原因仍須以修正後的明確錯誤代碼或真實成功結果確認。
- 第二輪修正要求生成與備援均符合已選食材、實際數量、本餐確認的調味料、份數與登記設備；無可行備援就清楚失敗。料理包保存前對齊庫存 key／單位，非調味料不可被模型標記為免扣庫存。
- 請求直接帶入指定份數，避免把食材倍乘但保留原份數的步驟文字。前端顯示本餐總用量，鹽油採本餐可用確認而非新增未知總庫存。
- 第二輪完整 `bun run verify` 通過：196 項單元／API、Web build、API typecheck、31 項瀏覽器測試。正式 AI 成功、下廚、實際餐份、庫存扣除與 EXP 尚待驗證。

## OpenRouter 403 實際根因

- 正式 Render 服務已部署 PR #33，實際食譜呼叫回傳 `OPENROUTER_403`。在不輸出憑證的情況下，使用該服務既有金鑰查核 OpenRouter，確認金鑰累計上限 USD 200、已用 USD 200.005462966、剩餘上限 0。
- 一次最小請求回傳 HTTP 403，`metadata.limit_source=openrouter_key_limit`、`scope=key_limit`，訊息為 `Key limit exceeded (total limit)`，上限不自動重設。帳號總額度 498、總用量 491.828584272，仍有約 USD 6.17；不能把這個錯誤說成模型不存在或帳號無額度。
- 使用者確認本次登入的是新註冊帳號，不能管理正式服務的原金鑰。上限調整與原帳號登入待使用者確認，尚未修改正式憑證或增加支出範圍。
- 程式只依供應商明確的 key-limit metadata 回傳安全錯誤代碼，顯示服務金鑰上限已達；其他 403 保持一般拒絕，不猜測原因。供應商原始訊息與金鑰不傳給使用者端。
- 新帳號初次設定自動產生的一把未使用金鑰曾進入頁面檢查輸出，已撤銷並確認清單只剩另一把未使用金鑰；正式服務金鑰未進入輸出。
- 第一餐生成成功、實際料理、庫存扣除、餐份及 EXP 仍未完成。

## 使用者選擇暫停 AI 後的第一餐路徑

- 使用者選擇保留 USD 200 上限，暫不啟用 AI。未調高上限、未儲值、未替換正式金鑰；後續第一餐不用 OpenRouter。
- 補入固定文字食譜「快煮鍋小白菜蛋花湯」：2 人份，小白菜 250 克、雞蛋 4 顆、飲用水 600 毫升、鹽 2 克。使用既有 curated seed 機制與確定性規則檢核，不冒充模型生成、獨立 AI 審查或實體試做。蛋料理食安參照既有 FoodSafety.gov 來源；包含蛋花完全凝固、71°C 與容量不足分批提醒。
- 自由搭配已有完全符合庫存、已確認調味料、份數及設備的發布食譜時，直接提供該食譜，`source=catalog`、`aiAttempted=false`；不先呼叫 AI。未確認鹽或缺少小白菜時不得提供這道料理。
- 此道沒有可靠的估價資料，成本欄位為 0，預覽顯示「成本待確認」，不宣稱免費。完成結算仍依真實批次與使用者實際餐份，不預先扣庫存或發 EXP。
- 完整 `bun run verify` exit 0：201 項單元／API、Web build、API typecheck、31 項瀏覽器測試通過。既有 Fast Refresh warning 與 mock health proxy 訊息不影響通過結果。發布與正式站預覽待驗證；實際料理與結算仍待使用者完成。
